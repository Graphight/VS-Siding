# Shake styles

- Status: Draft
- Created: 2026-09-25
- Reflects: decisions 0017, 0022, 0027; `wall.json`'s `shakes-{wood}` entry; `VSSiding.Tests/WallShapeGen.cs`'s `front-shakes`/`secondfront-shakes`/`back-logs` groups; `PlaceWallFrame`

## Summary
A finished log wall is shakes outside and hewn logs inside, always.
That is decision 0027's plank problem: the front/back split is geometric, not indoor/outdoor, so an interior partition or a room-side build puts shakes indoors on one face.
Planks fixed this with two tool modes on the plank item.
Logs carry no siding behaviour, so there is no mode to pick from.
This proposal adds one, mirroring `PlaceWallFrame`'s `weatherboard`/`boards` pair, and works out what geometry a `logs` style needs that doesn't exist today.

## Context
`wall.json`'s `shakes-{wood}` finish entry (`FinishFamilies`, around line 208) reads:
```
Elements: { front: "front-shakes", back: "back-logs" },
```
with no `Styles` key.
Compare `planks-{wood}` a few lines above, which carries `Styles: ["weatherboard", "boards"]`.
The finish entry comes from the held item (`MatchConsumes(heldCode, ...)`, `SidingWallBlock.cs:308`), and a held log has no tool modes, so no style ever reaches it.
A shake finish always lands as `front-shakes` on the front and `back-logs` on the back.

The two faces are not symmetric options.
`front-shakes` (`WallShapeGen.cs` lines 187-218) is decision 0022's tiled relief profile: four shakes per course, six courses, each with its own butt/body depth pair, position-mapped UVs so painted courses land on the stepped lips and carry across stacked walls.
`back-logs` (lines 219-223) is a flat half-depth slab with four proud horizontal logs, log-cabin style, also position-mapped.
Neither is weatherboard's or plank-boards' shape reused — decision 0022's whole point was that shakes and weatherboard only share a box count, not a silhouette.
So today's two faces are "shakes" and "logs", and there is no second shakes-side option and no second logs-side option: only one geometry exists per face.

Planks solved the front/back mismatch by letting the player choose which *style* — weatherboard or flat boards — goes on which face, keeping one geometry pair (`front-weatherboard`/`back-boards`) and mirroring it onto the other face (`front-boards`/`back-weatherboard`).
Logs need the same choice: shakes outside, logs inside, or the reverse.
That means a `front-logs` and a `back-shakes` group, not a reuse of planks' `front-boards`/`back-weatherboard` — a log-cabin face and a plank-board face are different woods and different geometry, and courses in shakes cost 96 rows in the element table (decision 0022) specifically because they aren't a flat profile.

## Design

**Two new element groups, mirroring the two that exist.**
`front-logs`: the `back-logs` box list, moved onto the `front` face and given `RunAxis`/positional UVs consistent with how `front-shakes` samples the texture positionally, so a `front` and `back` mirror the way `front-weatherboard`/`back-weatherboard` already do.
`back-shakes`: `front-shakes`'s tiled relief profile, moved onto the `back` face.
Both need a `secondfront-*` counterpart (`secondfront-logs`) for `cornerout.json`, matching how `secondfront-boards` was added in decision 0027 and `secondfront-shakes` already exists from decision 0022.
Generated by `WallShapeGen` and `just shapes`, same as decision 0027's plank mirrors — no hand-edited JSON.

**Element names follow `{face}-{style}`,** exactly as decision 0027 set out: `front-shakes`/`back-shakes` for the `shakes` style, `front-logs`/`back-logs` for the `logs` style.
`SelectiveElements` already resolves this pattern; no code change needed there.

**`shakes-{wood}` gains `Styles: ["shakes", "logs"]`,** the same list shape as `planks-{wood}`'s `Styles: ["weatherboard", "boards"]`.
Default `Elements` stays `{ front: "front-shakes", back: "back-logs" }`, unchanged, so a wall nobody restyles looks exactly as it does today.

**Placed logs gain a `CollectibleBehavior` with tool modes, patched on the way `plank-frame-behavior.json` puts `PlaceWallFrame` on planks.**
The finish click already lands on the wall: `SidingWallBlock.OnBlockInteractStart` reads the held stack's mode through `ResolveStyle(PlaceWallFrame.ToolModeOf(slot))` (`SidingWallBlock.cs` line 254).
`ToolModeOf` is just the stack's `toolMode` int attribute, so it reads a log stack exactly as it reads a plank stack; the new behaviour only has to offer modes and store the choice.
What doesn't carry over is the numbering.
`ResolveStyle` maps 2 to `weatherboard` and 3 to `boards`, and 0 and 1 are plank frame modes, so a log's mode 0 must mean "the entry's `Elements` default", or every log in an existing save would wake up forcing one style.
So logs get three modes, `default`, `shakes`, `logs`, and `ResolveStyle` takes the held collectible into account (or logs use indices 4 and 5), keeping the append-only rule its comment states.

**Icons.** Two more mode-picker SVGs (`shakes.svg`, `logs.svg`), tinted the same `-1` white as the existing four, per decision 0031's icon convention.

## Alternatives considered
- **Reuse `front-boards`/`back-weatherboard` for a log's alternate style.** Wrong wood, wrong geometry — those are plank profiles, and a log-cabin face reusing a flat-board mesh would show plank grain on a log wall.
- **Detect indoor/outdoor automatically, as decision 0027 already rejected for planks.** Same room-detection timing problem: walls finish before roofing, so almost every face would read as exterior.
- **A style toggle on the wall block instead of the held item.** Decision 0027 rejected a modifier key for planks already (0006 removed shift from the build flow); no new reason appears for logs.
- **Leave logs unstyled.** Consistent with today, but shakes indoors was seen in play, and the fix is the same shape as work already shipped for planks.

## Consequences & open questions
- Every placed log in the game gains a mode picker, including logs never meant for a wall.
- Open: indices 4 and 5 in the one `ResolveStyle` switch, or a switch per held collectible.
- `WallShapeGen`'s cost for decision 0022's tiled profile was 96 element-table rows producing thousands of lines of JSON; `back-shakes` inherits that cost, `front-logs` does not (it mirrors the cheap flat `back-logs` list).
- Restyling in place (decision 0027's "same material, different style is free") should carry over unchanged: a `shakes`-style face restyled to `logs` needs no re-break, same as boards/weatherboard today.
- No new finish material and no new item are introduced; this only adds a style axis to the existing `shakes-{wood}` entries.

## Stages
1. **Geometry:** `front-logs`, `back-shakes`, and their `secondfront-logs` cornerout mirror, generated via `WallShapeGen`/`just shapes`; add all three to every `ignoreElements` list per shape.
2. **Behaviour:** the log `CollectibleBehavior` with `shakes`/`logs` tool modes and its two icons; `Styles: ["shakes", "logs"]` on `shakes-{wood}`.
3. **Playtest:** both faces of a partition, both cornerout legs, restyling in place, a stacked shake wall for course continuity.
4. **Graduate** as a new decision extending 0027 and 0022.
